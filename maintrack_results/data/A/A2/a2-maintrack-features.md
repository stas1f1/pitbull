# A2 — слой признаков: полный main-track прогон

Дата: 2026-10-18. Все численные результаты ниже получены отдельными прогонами
для `PLAN_main_track.md`; прежние эксперименты и ответы моделей не включены.

## Вопрос и правило

Проверяется, меняется ли результат программы признаков для момента `t`, если
полную базу `D` заменить её состоянием `D|t`. `LEAK` означает исполнимое
различие, `CLEAN` — отсутствие различия в проверенной области. `ERROR` и
неизвестная доступность столбца не перекодируются в `CLEAN`.

Вердикт шага — `positive`, если свежий исполнимый прогон на реальных данных
даёт детерминированную утечку при чистом отрицательном контроле. Масштаб
вывода указывается отдельно для каждой части корпуса.

## Экспертный SQL

Проверены все 15 файлов `audit/`: F1 (3), Event (3), Stack (3), Amazon (4),
H&M (2). Для каждого основного файла использованы три момента времени,
проверка детерминизма и отрицательный контроль. Запуск последовательный,
`threads=1`, с лимитом памяти DuckDB. Для крупных таблиц Event/Stack взято до
100 000 исходных строк, Amazon/H&M — до 1 000 материализованных строк;
поэтому их `CLEAN` не означает чистоту полной базы.

- F1: 9/9 основных ячеек `LEAK`; механизм — признаки следующих гонок.
- Event: 6/9 `LEAK`, 3/9 `CLEAN`; часть находок смешана с A1/C4 и полями с
  неизвестной доступностью.
- Stack `post-votes`: 2/3 `LEAK`; `user-badge`: 1/3 `LEAK`.
- Stack `user-engagement`: `ERROR`, потому что локальная таблица `posts` не
  содержит `AcceptedAnswerId`; результат `uncheckable`, не `CLEAN`.
- Amazon и H&M: основные ячейки `CLEAN` только на ограниченных
  материализациях.
- Все исполнимые отрицательные контроли `CLEAN`; детерминизм пройден, кроме
  schema-incompatible `user-engagement`.

Артефакты: `rel/out/sql_oracle_maintrack_2026-10-15_*.csv`, smoke-файлы в
итог не включаются.

## Featuretools

Четыре схемы (`f1`, `stack`, `event`, `amazon`) × пять seed × три режима:

- D1, без отсечки строк: 20/20 `LEAK`;
- D2, строки отсечены, поздний столбец не замаскирован: 20/20 `LEAK`;
- D3, строки и доступность столбцов ограничены: 20/20 `CLEAN`.

Это контролируемый реляционный benchmark двух механизмов, а не замена аудита
естественных SQL-программ. Артефакты:
`results/maintrack_2026-10-15/a2_featuretools.csv` и summary JSON.

## Самописный код вместо внешней LLM

По прямому указанию пользователя недоступная внешняя LLM-ячейка заменена
новыми вручную написанными программами для `rel-f1`, `rel-stack`, `rel-event`
и `rel-amazon`. Это отклонение **не измеряет поведение LLM** и не использует
старые ответы. На каждой базе взяты три квартильных момента и 24 сущности;
для выбранных сущностей сохранена вся история событий без лимита строк.

- unbounded-агрегации: 12/12 `LEAK`;
- те же программы с `event_time <= seed_time`: 12/12 `CLEAN`;
- обработано 14 387 реальных строк событий;
- время 2,1 с, RAM в конце 101,7 МБ, один CPU-поток.

Артефакты: `results/maintrack_2026-10-18/a2_handwritten.csv`, summary JSON;
код — `experiments/maintrack_a2_handwritten.py`.

## Вердикт

**positive / подтверждено для слоя признаков.** Дифференциальный принцип
обнаружил детерминированные нарушения в экспертном SQL, Featuretools и новом
самописном коде, а отрицательные контроли остались чистыми.

Ограничения: LLM по исходному протоколу заменена пользователем на самописный
код; Amazon/H&M SQL проверены на ограниченных материализациях; один Stack SQL
несовместим с локальной схемой. Поэтому нельзя утверждать долю утечек LLM или
полную чистоту остальных файлов.
