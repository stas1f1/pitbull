### Ошибка на единицу (`include_cutoff_time`) — **не подтвердилась**

**D2 минус D3 = ровно 0.00 на всех задачах и моментах.** Порог «хотя бы 1 п.п.» не взят.

Причина понятна и её стоит записать: `include_cutoff_time=True` меняет результат только для событий, попавших **ровно** в момент отсечки. Метки Olist поставлены на полночь первого числа месяца, а `order_purchase_timestamp` — с точностью до секунды; событий ровно в полночь практически нет. **Отсюда содержательный вывод: эта ошибка на единицу опасна на данных дневной гранулярности, где в момент отсечки попадает целый день событий, и безвредна на данных с точным временем.** Как самостоятельный результат для статьи не годится — нужна база с датами без времени.

### Что осталось непроверенным

Набор признаков — общий featuretools (`count/sum/mean/max/min/std`, глубина 2, 13–22 признака), поэтому базовый AUC ниже, чем у ваших ручных генераторов в `rel/` (0.63–0.66 против 0.72–0.75 на C). Сравнения внутри P1 это не искажает — режимы отличаются только отсечкой, — но абсолютные числа с `RESULTS.md` сопоставлять нельзя.

## Оракул для P3 — написан и провалидирован (§4 шаг 1)

`oracle.py` — дифференциальное исполнение. `test_oracle.py` — валидация на эталонах из `rel/`. **18 комбинаций эталон × момент, все размечены верно:**

| эталон | ожидалось | вердикт |
|---|---|---|
| корректно (отзыв по дате написания) | чисто | **чисто** |
| утечка только в своей истории | нарушение | **нарушение** (6/10 колонок) |
| **утечка ТОЛЬКО через соединение** | нарушение | **нарушение** (6/10) |
| утечка в обеих группах | нарушение | **нарушение** (10/10) |
| отсечки нет нигде | нарушение | **нарушение** (10/10) |

Ключевое: режим «утечка только через соединение» — тот самый, где одномерная проверка не двигается ни на тысячную, — оракул ловит уверенно. **Ровно то, ради чего он и нужен.**

### Побочная находка: эталон «корректно» из `rel/` сам протекает

При первом прогоне оракул объявил нарушение на **корректном** эталоне — расходились ровно 2 колонки из 10: `own_review_mean` и `nbr_review_mean`.

Это не сбой оракула. В `leak_multi2.py` / `leak_multi3.py` `review_score` приджойнивается к заказу по `order_id`, а фильтрация идёт по **времени заказа** (`ev.ts <= cutoff`), а не по времени написания отзыва. Отзыв же пишется позже заказа: медиана 10 дней, 90-й перцентиль 23 дня, максимум 147.

**Измерено: 5.06% заказов, размещённых до момента предсказания, имеют отзыв, написанный после него.** То есть базовый вариант, помеченный как «корректный», читает будущее — через побочную таблицу с собственной временной осью. Это ровно тот класс утечки, ради которого затевается вся работа, и он оказался в вашей же эталонной реализации.

Проверено прямо: тот же генератор с фильтром `review_creation_date <= момент` проходит оракул чисто на всех трёх моментах.

**Что с этим делать.** Величины завышения в `RESULTS.md` скорее всего устоят: утечка по отзывам присутствует одинаково во всех режимах, а завышение считается как разность. Но **базовый AUC в `RESULTS.md` слегка оптимистичен, и строка «корректно» называется так неверно.** Это стоит пересчитать до подачи — и, что важнее, это лучший из возможных аргументов в пользу вашего же инструмента: дифференциальное исполнение нашло утечку в тщательно написанном экспертном коде авторов, которые про утечки и пишут статью. Такой пример в статье дороже любой симуляции.

## P2 — опубликованные артефакты агентных систем

**Артефакты есть.** `RelAgent/case_study/rel-stack_user-engagement/`: **32 испытания**, `best_program.json`, `conversation_trace.jsonl` (248 строк), результаты на тесте. Итого **157 экземпляров запросов, 37 уникальных текстов SQL** — чужой опубликованный код признаков для многотабличной задачи с моментом предсказания. Выгружено в `p2_out/unique_queries.json`.

`autogluon-assistant`, `MetaGPT`, `aideml` — сохранённого сгенерированного кода признаков **нет**, проверять нечего.

**Результат: подтверждённых нарушений 0 из 37.** Автоскан подсветил 5, ручная проверка — все 5 ложные (отсечка через другой алиас `b.timestamp`; соединение с уже отсечённой таблицей; чтение только статических колонок справочника).

**Но это измерение условия «с предупреждением», а не наивного.** Промпт RelAgent (`src/relagent/scientist/prompts.py:60-61`) требует временной фильтр у **каждой** агрегации, повторяет это дважды и отдельно называет конкретный способ ошибиться: «never substitute the target entity's own creation timestamp … as the boundary».

Отсюда:
1. **Прямого свидетельства в пользу пункта (в) нет.** Заявлять «агентные системы порождают протекающий код» со ссылкой на RelAgent нельзя.
2. **Косвенное свидетельство сильное.** Две плотные строки промпта, защищающие от конкретного failure mode, не пишут про проблему, которой не видели. Формулировать надо именно так — как свидетельство из промпта, а не из кода.
3. **Для P3 это меняет приоритет:** условие P2 уже измерено за нас и там ноль. Ценность P3 теперь целиком в разнице **P0 против P1**.

### Побочно: +11.5 п.п. от смены модели, а не признаков

Испытания 10–22 используют **побитово одинаковый** набор признаков (хеш `a29be521`). LightGBM `dart`/`goss` дают 0.765–0.788, XGBoost и CatBoost — 0.897–0.899.

**Величина, которой вы измеряете утечку (7–11 п.п.), здесь достигается простой сменой бустера.** Значит скачок качества в траектории агента сам по себе не диагностичен, и завышение обязано измеряться при фиксированной модели.

## P7 — аудит экспертного SQL: закрыт

Архив не понадобился — корпус публичен: `snap-stanford/relbench-user-study`, **15 файлов `feats.sql`, 172 соединения**. Обе цифры сходятся с вашими.

Проверены руками все 6 оставшихся мест:

| место | вердикт |
|---|---|
| `amazon/item-churn :: customer_feats` | ложная тревога — отсечка через отдельную таблицу моментов (`timestamps.timestamp > review.review_time`) |
| `amazon/user-ltv :: product_ratings` | ложная тревога — та же конструкция |
| `stack/post-votes :: vote_stats_first_month` | ложная тревога в контексте — используется только через `owner_feats_by_timestamp` |
| `stack/post-votes :: comment_stats_first_month` | ложная тревога в контексте — то же |
| `stack/post-votes :: owner_feats_by_timestamp` | ложная тревога — соединение с `posts as censored_posts` по `date_diff(CreationDate, timestamp) > 30`, окно «первого месяца» целиком в прошлом. Цензурирование сделано сознательно |
| `stack/user-badge :: badge_freqs` | **НАСТОЯЩЕЕ НАРУШЕНИЕ.** `count(*) / sum(count(*)) over ()` по всей таблице `badges`, без отсечки и без колонки момента. В **двух** файлах, в обоих утекает в признаки (`rarity`, `badge_score`) |

**Итог: 2 настоящих нарушения на 172 соединения в опубликованном экспертном коде — около 1%.** Из 8 подсвеченных мест 6 ложных.

**Аргумент из §8 подтверждён и усилен.** Доля ложных тревог автоскана — **6 из 8 (75%)**. Встретились как минимум четыре несовместимые синтаксические формы отсечки: соединение с таблицей моментов; коррелированный подзапрос с другим алиасом; цензурирование сущности по возрасту вместо фильтрации события; косвенная защита через уже отсечённую таблицу. Мой скан корпуса RelAgent дал ту же картину — 5 подсветок, 5 ложных. **Теперь это аргумент в пользу дифференциального исполнения против статического разбора, полученный на двух независимых чужих корпусах — экспертном и агентном. Плюс третий случай: оракул нашёл в вашем эталоне утечку, которую не увидел никто.**
