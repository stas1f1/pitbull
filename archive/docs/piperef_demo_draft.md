## Abstract (≈150 слов, готово к правке)

> Modern AutoML systems — evolutionary (FEDOT), gradient-boosting-centric (LightAutoML), and stacking-based (AutoGluon) — as well as the new generation of LLM agents that drive them, all converge on the same final act: they rank candidate pipelines by a validation score and ship the winner. Recent evidence shows this act is where much of the remaining performance is lost. Selecting by test rather than validation score would add 9–13 percentage points of medals on MLE-bench; validation-to-test rank correlation has been measured at 0.71; and a large-scale study found that three silent misconfiguration bugs corrupted roughly 8,975 of 10,469 automated experiments before a human noticed, because agents reason at the specification layer and cannot verify the execution layer.
>
> We demonstrate **PIPEREF**, a framework-agnostic agentic trust layer that sits around — not inside — an AutoML run. Before the search, PIPEREF detects task-framing ambiguity and synthesises an explicit validation protocol. After the search, an LLM referee generates and executes dataset-specific falsification probes — target and temporal leakage, pre-split preprocessing leakage, group leakage, silent configuration drift, resplit instability — over the entire candidate set the AutoML framework produced, and re-ranks candidates by evidence of robustness rather than by validation score alone. PIPEREF runs on CPU with commodity LLM API calls at roughly $0.3 per dataset. Our demonstration lets attendees inject a leak into a live dataset and watch the validation leader fall while the referee's choice holds on held-out data.

## 1. Introduction (≈0.75 колонки)

Структура в трёх ходах:

**Ход 1 — область выросла, но упёрлась не туда, куда думает.**
За 2025–2026 гг. агентный AutoML прошёл путь с 16.9% до 65.3% medal rate на MLE-bench. Но три независимых контролируемых исследования 2026 года показали, что дальнейшие вложения в *механизм поиска* дают убывающую отдачу: жадный hill-climber почти не уступает лучшему tree-search агенту (FML-bench); байесовская оптимизация гиперпараметров одной промежуточной программы сравнялась или превзошла полный эволюционный прогон в 13 из 15 случаев (ZIB); при равном бюджете классические TPE/SMAC/CMA-ES опережают LLM-предложенцев (Hutter et al.).

**Ход 2 — где на самом деле теряется качество: отбор и верификация.**
Три числа, каждое из чужой статьи, каждое проверяемое:
- **+9–13 п.п.** медалей, если выбирать финальное решение по test, а не по val (AIRA, Meta FAIR);
- **ρ = 0.7059** — ранговая корреляция val↔test на 10 469 автоматических экспериментах (Orze);
- **~8 975 из 10 469** экспериментов испорчены тремя тихими мисконфигурациями до вмешательства человека, потому что *«LLM-агенты работают на уровне спецификации и не могут верифицировать уровень исполнения кода»*.

Плюс два ортогональных: агенты молча выбирают неверный таргет в **39–63%** неоднозначных задач (Ambig-DS), а сокрытие входных данных роняет качество агента лишь на **15–18%** (KramaBench) — то есть часть «успеха» вообще не про данные.

**Ход 3 — чего не хватает и что мы даём.**
Выделенную верификацию сегодня поставляют только MLE-STAR (два чекера) и AutoKaggle (юнит-тесты), обе — внутри собственного агента. Статические детекторы утечек (LeakageDetector 2.0) не понимают контекста датасета; верификаторы агентных трасс проверяют рассуждение, а не ML-пайплайн. **Никто не построил слой, который аудирует и переотбирает кандидатов, произведённых произвольным AutoML-фреймворком.** PIPEREF — такой слой.

**Вклад (буллетами, обязательно для demo-статьи):**
1. Framework-agnostic слой доверия поверх FEDOT, LightAutoML, AutoGluon и голых sklearn-пайплайнов, работающий с *полным множеством кандидатов*, а не только с победителем.
2. LLM-генерация и исполнение **датасет-специфичных фальсифицирующих проб** поверх фиксированного ядра из N детерминированных проб.
3. **Переотбор по робастности** вместо val-скора, и синтез явного протокола валидации до запуска поиска.
4. Интерактивная демонстрация с инъекцией утечки в реальном времени.
5. Открытый код и воспроизводимый стенд, работающий на CPU за ~$0.3/датасет.

## 2. System Architecture (≈1 колонка + рисунок)

**Рисунок 1** (обязателен): три блока слева направо, AutoML-фреймворк в центре как чёрный ящик.

```
             ┌──────────────── PIPEREF ────────────────┐
             │                                          │
  dataset ──►│ ① PRE-FLIGHT          ③ POST-FLIGHT     │──► ranked
  + task     │   framing check          probe battery   │    candidates
  descr.     │   protocol synthesis     evidence report │    + audit
             │        │                      ▲          │      report
             └────────┼──────────────────────┼──────────┘
                      ▼                      │
              ┌───────────────────────────────────┐
              │  ② AutoML backend (black box)     │
              │  FEDOT / LightAutoML / AutoGluon  │
              │  / sklearn Pipeline               │
              └───────────────────────────────────┘
                     returns FULL candidate set
```

### 2.1 Pre-flight: framing check + protocol synthesis
Агент получает схему датасета, статистики по колонкам, сэмпл строк и текстовое описание задачи. Детектирует четыре класса недоспецификации:
- **неоднозначность таргета** (несколько правдоподобных целевых колонок / несколько формулировок задачи);
- **неоднозначность метрики** (несбалансированные классы без указания метрики; asymmetric cost);
- **скрытая групповая структура** (квази-идентификаторы, повторяющиеся сущности → нужен GroupKFold);
- **временная ось** (датовые/временные колонки → нужен temporal split, а не случайный).

Ключевая деталь, отличающая нас от простого «спроси у пользователя»: **калибровка порога вопроса**. Ambig-DS показал, что агенты систематически либо переспрашивают на ясных задачах, либо молча ошибаются на неясных. Мы задаём вопрос только когда апостериорная энтропия по кандидатным фреймингам превышает порог; иначе фиксируем фрейминг и **логируем допущение** в отчёт.

Выход блока — исполняемый **валидационный протокол** (объект-сплиттер + метрика + правила предобработки), который передаётся бэкенду.

### 2.2 Backend adapters
Тонкие адаптеры, извлекающие из каждого фреймворка **всё множество кандидатов**, а не только победителя:
| Бэкенд | Что извлекаем |
|---|---|
| FEDOT / GOLEM | полная история поколений (`api.history`), графы пайплайнов, фитнесы |
| LightAutoML | внутренние модели + веса блендера |
| AutoGluon | leaderboard всех обученных моделей + стек-уровни |
| sklearn | пользовательский список пайплайнов |

Единое внутреннее представление: `(pipeline_object, fit_predict_callable, val_score, provenance)`.

### 2.3 Post-flight: probe battery + referee
**Ядро — детерминированные пробы** (исполняются всегда, без LLM):
1. **Adversarial validation** train vs test — если классификатор различает сплиты с AUC ≫ 0.5, распределения разъехались.
2. **Target-leakage probe** — единичный признак, дающий подозрительно высокий скор; permutation importance с проверкой на «слишком хорошо».
3. **Temporal-order probe** — обучение строго на прошлом vs случайный сплит; расхождение = временная утечка.
4. **Pre-split preprocessing probe** — интроспекция пайплайна: подгонялись ли imputer/scaler/target-encoder до сплита.
5. **Duplicate / group-leakage probe** — пересечение (квази-)дубликатов и групп между train и test.
6. **Resplit stability** — K бутстрэп-респлитов, дисперсия скора кандидата.
7. **Silent-config probe** — сверка заявленной конфигурации с фактически применённой (то, на чём погорели 8975 экспериментов Orze).
8. **Data-usage probe** (в духе MLE-STAR) — все ли предоставленные источники реально использованы.
9. **Shortcut probe** (в духе DSGym/KramaBench) — насколько падает качество, если зашумить/скрыть ключевой источник; если почти не падает, модель не про данные.

**LLM-слой поверх ядра** — генератор проб, специфичных для датасета: агент читает схему + описание и пишет **исполняемый тест-кандидат** на гипотезу утечки, которая не покрыта ядром (например, «колонка `discharge_date` не может быть известна на момент предсказания»). Тест исполняется в песочнице; в отчёт попадает и код, и результат. Это принципиально: **отчёт содержит доказательства, а не мнение LLM.**

**Рефери.** Итоговый ранг кандидата:

$$ R(c) = s_{val}(c) - \lambda \sum_{p \in P} w_p \cdot \text{penalty}_p(c) - \mu \cdot \sigma_{resplit}(c) $$

где penalty — бинарный/градуированный штраф пробы, σ — дисперсия по респлитам. Веса $w_p$ фиксированы и опубликованы (не подбираются на тестовых данных — это важно проговорить, иначе рецензент справедливо спросит).

## 3. Demonstration Scenario (≈0.75 колонки — **для demo-трека это самый важный раздел**)

Три сценария у постера, каждый ≈2 минуты:

**Сценарий A — «Сломай мой датасет».**
Посетитель выбирает датасет и одним кликом внедряет утечку из меню (добавить колонку, коррелирующую с таргетом; перемешать временной порядок; продублировать строки через сплит; подогнать scaler до сплита). Запускается AutoML (30–60 с на CPU). Дашборд показывает: **val-лидер набирает 0.97, рефери его отклоняет с красной карточкой «target leakage, evidence: probe #2 output», выбирает другого кандидата — и на скрытом holdout выигрывает именно выбор рефери.**

**Сценарий B — «Три фреймворка, один суд».**
Один датасет прогоняется через FEDOT, LightAutoML и AutoGluon. Показываем, что рефери — единый слой поверх всех трёх, и что дефекты, которые он ловит, у разных фреймворков разные (у FEDOT — структурные, у AutoGluon — стековые).

**Сценарий C — «Pre-flight».**
Подсовываем намеренно недоспецифированную задачу. Система задаёт **ровно один** уточняющий вопрос и показывает, во что превратился бы результат при неверном фрейминге (Δ метрики).

**Что физически на постере:** ноутбук с локально запущенным Streamlit/Gradio; QR-код на репозиторий и на видео; распечатанный пример audit-отчёта. Интернет на площадке не гарантирован — **держать LLM-часть с кэшированными ответами для оффлайн-режима**, иначе демо умрёт.
