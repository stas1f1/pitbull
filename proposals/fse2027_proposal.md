# PITBULL — финальный план подачи (FSE 2027, research track)

Статус: ревизия 3 (3 сентября 2026) — по второй критике
`critique/fse2027_rev2.md`: введены ярусы объёма A/B/C, устранена циркулярность
RQ2а, canary-прогон расширен на per-column значения прошлых строк, добавлена
стратификация по механизму утечки, сняты формулировки-перехлёсты. Пороги §7,
замороженные 2 сентября, не ослаблены; поправки 3 сентября — только добавления,
внесены до старта полных прогонов и датированы. **FSE — приоритетная подача;
ICLR-план подчинён (§11).** Дедлайн full paper: **2 октября 2026** (решение
22 января 2027, Major Revision 5 марта 2027). ~11 стр., double-blind.

Терминология: witness — расхождение выходов прогонов на полной и усечённой базе;
canary-прогон — прогон на копии, где возмущено ВСЁ, что усечение делает
недоступным (и будущие строки, и значения с поздней доступностью у прошлых
строк); held-out моменты — моменты проверки, не участвовавшие в вынесении
вердикта. Общее определение корректности, из которого оба прогона — частные
случаи: выход программы должен быть функцией только от D|t (усечение проверяет
φ(D,t) = φ(D|t,t); canary — φ(D,t) = φ(D',t) для D' с D'|t = D|t).

## 1. Центральный тезис

Дифференциальная проверка point-in-time корректности требует человека в четырёх
местах: объявить карту доступности, написать адаптер, дать корректную
реализацию-эталон, выбрать моменты проверки. Эталон не нужен для вердикта — его
заменяет инвариант (код сравнивается сам с собой); в плане он используется в одной
роли: для оценки подлинности исправлений, и это проговаривается в статье одной
фразой. Статья устраняет ещё два шага и честно называет последний:

> **Цикл дифференциальной проверки кода признаков замыкается без ручной
> подготовки:** карта доступности выводится из схемы и данных, два разнесённых
> момента дают детекцию ~100% для доминирующего класса утечек, и цикл «witness →
> исправление → верификация на held-out моментах» доводит N из M протекающих
> программ до чистых — при том что без чекера модель находит собственную утечку
> в 1 случае из 12. Остающийся ручной шаг — интерфейс программы (§6) — назван и
> измерен воронкой.

Главное число первой страницы — абсолютный исход RQ0: «N из M протекающих
программ доведены до чистых без единого ручного ввода, верифицировано на held-out
моментах; модель сама — 1/12». Согласие с ручной картой — валидация, не результат;
оно идёт второй строкой.

Кандидат заголовка (без отрицаний, не противоречит §6): «PITBULL: Closing the
Loop — Zero-Configuration Point-in-Time Testing and Repair of Generated Feature
Code». **Решение по имени (принято авторами 3 сент): проект и артефакт остаются
PITBULL; в рукописи на рецензию имя анонимизируется** (нейтральный плейсхолдер,
единой заменой перед подачей; PITBULL возвращается в camera-ready). Заголовок
рецензионной версии: «Closing the Loop: Zero-Configuration Point-in-Time Testing
and Repair of Generated Feature Code».

Опора односторонности (методологическая предпосылка в Approach, не вклад):
для произвольного чёрного ящика доказать отсутствие утечки невозможно; Fonseca
(TOSEM 2026) показывает, что свойство «утечки нет» не перечислимо уже при
доступности, зависящей от значений. Формулировка в статье: «никакой метод общего
назначения не доказывает отсутствие; дифференциальный тест полон по
свидетельствам» — слово «оптимален» не употребляется (его собственный набор
специально сконструированных программ даёт 54.5% пропусков у двухпрогонного
детектора; полнота по witness'ам в пределе ≠ доля детекции при конечном бюджете).
Его future work №2 — вывод структуры доступности из реальных фреймворков — это
наш RQ1. Его набор утечек цитируется как доказательство существования, не
частоты; группы с нулём событий отчитываются как 0/n с границей по правилу трёх.

## 4. Research questions (метрики уточнены по критике ревизии 2)

**RQ0 (главный). Даёт ли полный цикл под автоматически выведенной картой те же
вердикты и ту же верификацию исправлений, что под ручной?** Сквозной прогон
«mapinfer → выбор моментов → усечение + canary → witness → исправление →
верификация» под авто-картой против того же цикла под ручной. Метрики: согласие
вердиктов и исходов верификации с направлением расхождений (LEAK→CLEAN —
пропуск, CLEAN→LEAK — ложная тревога; знаменатель — пары программа×момент).
Причина RQ0: под неверной картой вердикт и верификация ошибаются согласованно.

**RQ1. Какую часть карты доступности можно вывести там, где её никто не объявил?**
Честно: 25/34 таблиц — тривиальный `time_col` из метаданных RelBench; ценность —
Olist без метаданных, уровень отдельных колонок, колонки без канала. Baselines:
чтение метаданных + v0 + **LLM-карта**. **Пре-регистрированный исход (3 сент, до
прогонов): если LLM-карта не хуже эвристик v2 на per-column уровне — вклад RQ1
переформулируется в «проверяемость любой предложенной карты циклом» (RQ0
верифицирует карту исполнением), mapinfer подаётся как детерминированный запасной
вариант без API-вызовов.** Ручная per-column разметка пяти баз RelBench — два
аннотатора с каппой, внесена в календарь (§9). Статистика: каппа Коэна,
precision/recall по колонкам. Мотивация из литературы: карту сегодня пишут руками
(MDPI AI 245 — JSON-конфиг пользователя, «misconfiguration bypasses protections»);
Fonseca называет вывод структуры доступности своим future work.

**RQ2а. Находит ли LLM утечку чтением кода — и что даёт чекер сверх этого?**
LLM-детектор на всём наборе (61 протекающая + чистые + пары правильная/наивная из
демо, где истина известна по построению). Метрики — против вердикта чекера И
против известной истины на парах; **порог двумерный (поправка 3 сент): recall ≥
recall чекера − 0.1 И доля ложных срабатываний на чистых ≤ 0.1 — только оба
вместе меняют тезис на «чекер незаменим как верификатор»**. Отдельная строка
таблицы: чего у LLM-вердикта нет при любом recall — witness по значению,
расходящиеся колонки, моменты, верификация исправления исполнением. Ожидание из
литературы: Table 5 Draoui **согласуется** с нашим пилотом (не «подтверждает»:
другой класс утечки, другая ось — структура запроса, не именование концепции).

**RQ2б. Что именно исправляет цикл?** До матрицы — **разметка механизма утечки
каждой из 61 программы** (дёшево: witness называет колонки); CLEAN@k
стратифицируется по механизмам. Если механизм по сути один (join отзывов без
фильтра по дате) — это пишется числом и становится ограничением, а второе условие
(ярус C) выбирается с другим механизмом (per-column задержка доставки, «≤t vs <t»
на rel-f1). Матрица: {набор} × {F0-варианты, F0.5, F1} × модель-автор, n ≥ 3,
повтор запроса при no_code, k ≤ 5; CLEAN@k двумя числами; подлинность — состав
колонок + экспертная разметка (AUC — ярус C); верификация на held-out моментах.
Статистика: интервалы Уилсона; **кластерный бутстрап с кластером «программа» —
основной способ получить CI (запуски вложены в программы); Мак-Немар на уровне
программ — вторичный**. Названия и даты версий моделей фиксируются.

**RQ3. Сколько моментов нужно, что они стоят, и что ловит каждый уровень
вердикта?** Baseline — «тестовый момент бенчмарка» (rel-event: чист на нём,
протекает на 23/24). Плотность и кривая детекции от m; стратегии выбора моментов.
**Canary-прогон — исправленное определение (поправка 3 сент): возмущается всё,
что усечение делает недоступным, — будущие строки И per-column значения прошлых
строк с avail > t; обязательный контроль — naive-программа из Fig. 1 демо.**
Доля ложных срабатываний на шести базах с допуском, перекалиброванным под
возмущение (rel-amazon: 4 ложных вердикта из-за float в демо — прямой контроль);
формулировка «полное предупреждение» употребляется только если объём нулевой
группы (моменты × базы × программы, минимум n = 360) даёт границу правила трёх
≤ 1%. Таблица стоимости: время × размер × m × 3 прогона, деньги за LLM-части.

## 5. Наборы программ

Существующие: 61 протекающая генерация (все некорректные из 233, отбора не было;
механизм — размечается, §4 RQ2б), 2 агентных запроса, экспертный SQL (14
исполняемых). **Выборка реального кода — с воронкой как результатом:** критерий
отбора фиксируется до майнинга (есть момент прогноза: временной таргет или
временной сплит); отчёт по ступеням «найдено → имеет момент прогноза → уложилось
в интерфейс без правок → уложилось с обёрткой → отказ» («X из Y ноутбуков вообще
не определяют момент прогноза» — само по себе результат). Источники: Kaggle по
`olistbr/brazilian-ecommerce`; бенчмарк Draoui — **как образец методики майнинга,
не как источник образцов** (их 451 ноутбук — однотабличные sklearn про
overlap/preprocessing, временных многотабличных там почти нет). Контроль
запоминания: отложенный набор на переименованной схеме. Задел на журнальную
версию: Zenodo-пакет PLOS One (10.5281/zenodo.17745286).

## 6. Интерфейс программы (остающийся ручной шаг)

Python: `get_features(db, entity_ids, seed_time)` — одна точка времени на вызов;
реальные пайплайны считают по таблице пар (entity, seed_time) с построчным
cutoff, поэтому доля «без правок» ожидаемо мала, и это не провал, а измерение.
**Правила обёртки фиксируются заранее: обёртке разрешена перестановка вызовов
(цикл по моментам, переименование аргументов), запрещено касаться логики
признаков.** SQL: запрос с параметрами, возвращающий один результирующий набор
(сам запрос — многотабличный). Формулировка «произвольный код» в статье не
употребляется — «код в этом интерфейсе, как чёрный ящик».

## 7. Threats to validity

- **Construct:** знаменатель и направление согласия (RQ0); подлинность
  исправления — состав колонок + эксперты (+ AUC в ярусе C); карта таблиц ≠
  карта чекера — измеряются обе; RQ2а — метки чекера не истина, истина только на
  парах по построению.
- **Internal:** исправляет модель-автор (контроль — ярус C); canary меняет
  уровень шума допуска (перекалибровка); no_code — повтор запроса + два числа;
  недетерминизм — зёрна, повторы, отрицательный контроль до измерений.
- **External:** пилот — одна задача, одна база, вероятно один механизм утечки →
  разметка механизмов (ярус A), второе условие (ярус C); выборка реального кода.
- **Conclusion:** доли с интервалами Уилсона; CI из кластерного бутстрапа по
  программам; 11/12 без интервала не публикуется.
- Абзац о цене ошибок в workflow (закрывает «кому это помогает»): ложное
  срабатывание → очередь ручной проверки (§8 описывает режим); пропуск →
  инфляция до +16 AUC (демо); ручная подготовка → минуты инженера на четыре
  шага против нуля.

  «чекер = верификатор + локализатор» не слабее.
- Однородность механизма утечки может свести RQ2б к «одному фильтру» — тогда это
