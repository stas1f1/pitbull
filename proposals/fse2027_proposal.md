# PITBULL — финальный план подачи (FSE 2027, research track)

Статус: **план зафиксирован 1 сентября 2026 по результатам пилотов**
(`pilot/REPORT.md`; сырые данные в `pilot/`). Дедлайн full paper: **2 октября 2026**
(нотификация 22 января 2027, Major Revision 5 марта 2027). ~11 стр., double-blind.
Предыдущая редакция плана — в истории git; скан литературы —
`proposals/lit_scan_2026-08.md`.

---

## 1. Центральный вопрос

Код признаков для многотабличных задач всё чаще пишут LLM, агенты и
AutoML-библиотеки, и он систематически читает будущее (наши измерения: 62%/22%
некорректных генераций, +16.3 AUC у featuretools из коробки). Дифференциальное
исполнение даёт witness нарушения без чтения кода, но сегодня требует человека:
карта доступности, адаптер, референс, выбор моментов.

> Можно ли проверять point-in-time корректность произвольного кода признаков на
> произвольной реляционной базе без ручной подготовки — и замыкается ли без
> человека весь цикл: найти протекающую программу, довести её до чистой,
> подтвердить починку исполнением?

## 2. Заявления статьи (зафиксированы; каждое уже имеет пилотную опору)

- **C1.** Карта доступности выводится из схемы и данных автоматически для
  большинства таблиц; ошибки образуют один понятный класс «дата-не-канал».
  Пилот: 32/34 таблиц (0.94) двумя эвристиками без LLM.
- **C2.** Вердикт двухуровневый: точный witness по значению + полное
  предупреждение по чтению (канареечный прогон). Пилот: на кейсе совпадения
  witness 11/20, канарейка 19/20; ложных тревог 0 на всех контролях.
- **C3.** Плотность нарушения измерима, и для доминирующего класса утечек она
  высока: 2–3 разнесённых момента дают детекцию ~100%; проверка дёшева. Пилот:
  20/20 программ корпуса с плотностью 0.94–1.00; кривая детекции m=1 → 0.947,
  m=2 → 1.000.
- **C4.** Цикл «детекция → починка → верификация» замыкается без человека: модель
  чинит свой код за одну итерацию по одной фразе, но сама утечку НЕ находит —
  чекер незаменим именно как детектор и верификатор. Пилот: F0 = 1/12
  (единственный «успех» — удалением признаков), F1 = 11/12, F3 = 11/12, все
  успешные починки семантические.
- **C5 (одностороннее).** Полная сертификация невозможна в принципе
  (неразрешимость value-dependent доступности, arXiv 2607.04958); честный вердикт
  всегда «no witness at the m tested seed times» с ожидаемой детекцией из
  измеренной плотности.

Убрано по итогам пилота: заявление «witness как обратная связь превосходит
текстовую подсказку» (F3 ≈ F1; эффект живёт между F0 и F1 и уходит в ICLR-статью).

## 3. Research questions, метрики, что осталось сделать

**RQ1 — карта.** Эвристики v2 поверх пилотных v0/v1: (а) сигнал «значения колонки
систематически позже времени строки/родителя» → не канал создания (закрывает оба
пилотных промаха: shipping_limit_date, dob); (б) per-column каналы задержки
(доставка, ответ на отзыв) — вывод и оценка против ручной per-column карты Olist
и f1; (в) детекция undecidable-колонок (order_status). Метрики: per-table
accuracy (пилот: 0.94), per-column precision/recall, и главная — **сквозное
согласие вердиктов** прогонов чекера под авто- и ручной картой на существующих
корпусах (цель ≥ 0.9).

**RQ2 — цикл.** Полная матрица починки: {61 некорректная генерация + 2 агентных
запроса + экспертный SQL с нарушениями} × {F0, F1, F3} × ремонтник-автор,
n ≥ 3 сида, ретрай при no_code (пилотный артефакт), k ≤ 5. Метрики: CLEAN@k,
итерации, semantic vs deletion (по составу колонок И по AUC фиксированного
learner'а против корректного референса — в пилоте AUC-контроля не было),
верификация починки на держанных моментах (не тех, что дали witness). Плюс
holdout-корпус на переименованной схеме (контаминация).

**RQ3 — моменты.** Кривая детекции по плотности (пилотная методика) на
разреженных случаях: «≤t vs <t» на rel-f1 (дневная гранулярность), rel-event
(чист на 1 из 24); канарейка на этих же случаях (её вклад там, где witness
разрежен: пилотный naive_max — 0.55 против 0.95). Стратегии выбора моментов:
случайная, стратифицированная, адверсариальная — при бюджете m.

## 4. Дизайн и дисциплина

Негативные контроли до измерений (правило подтверждено пилотом: контроль 0/20);
фиксированный learner для всех AUC; версии окружения закреплены (pandas 2.2.3,
numpy 2.2.6 — на pandas 3.x детектор колонок уже ведёт себя иначе, это теперь
методическое правило); пре-регистрированные пороги (§6); критерии не толкуются
задним числом. Тяжёлые прогоны — на nss-calc2 (18 ядер), большие parquet читать
только потоково.

## 5. Конфаунды (обновлено по пилотам)

1. Ошибка карты ≠ утечка: RQ1 меряется против ручной карты до заявлений RQ2;
   witness-precision под авто-картой отдельно.
2. Починка выбрасыванием — **наблюдена в пилоте** (единственный F0-успех):
   классифицируется по составу колонок + AUC, рапортуется отдельной категорией.
3. Недетерминизм: фикс-сиды, повторы, допуск из негативного контроля.
4. Канарейка: (а) хрупкость — падение прогона 3 = «неприменима», не вердикт;
   (б) нечувствительность к возмущению сдвигом (count будущих строк канарейка не
   видит — ловится усечением; уровни дополняют друг друга в обе стороны, сказать
   это в статье явно).
5. Контаминация: holdout на переименованной схеме; сравнение brake rate
   публичная/анонимизированная версия — само по себе результат.
6. Верификация починки на тех же моментах, что и вердикт, — запрещена; держанные
   моменты обязательны (плотность 0.94–1.00 делает это дёшево).

## 6. Пороги и исходы (обновлены: часть уже разрешена пилотом)

- RQ1: порог «согласие < 0.8 → таксономия» на per-table уровне ПРОЙДЕН (0.94).
  Новый порог для camera-версии: сквозное согласие вердиктов ≥ 0.9 → статья-
  инструмент; 0.6–0.9 → инструмент с human-review очередью для класса
  «дата-не-канал»; < 0.6 → таксономия (маловероятно по пилоту).
- RQ2: замыкание цикла подтверждено; порог полной матрицы — CLEAN@5 ≥ 0.8 с
  ретраем no_code. Если деградирует на holdout-корпусе → секция про контаминацию
  становится результатом.
- RQ3: если на rel-f1/rel-event адверсариальный выбор не превосходит
  стратифицированный — рапортуем это честно, стратегия по умолчанию =
  стратифицированная (проще и воспроизводимо).

## 7. Каркас статьи

1. Intro: пример + числа источников нарушений (из ICDM-базы, с цитатой демо).
2. Approach: инвариант, witness, карта как гипотеза (mapinfer), двухуровневый
   вердикт (канарейка), одностороннесть через неразрешимость.
3. Closing the loop: F0/F1/F3, роль чекера = детекция + верификация.
4. Evaluation: RQ1 (34 таблицы + per-column + согласие вердиктов), RQ2 (полная
   матрица), RQ3 (плотности, кривая детекции, разреженные случаи).
5. Related work (по lit_scan: статика/LLM-чтение; 2607.04958 и бэктестинг-кластер;
   feature stores; APR; коммерческие пробы).
6. Limitations: один домен схем, ярусы моделей, value-coincidence за пределами
   сдвиговой канарейки, карта = модельное решение.

## 8. Календарь (двухнедельные циклы, старт 1 сентября)

- **Цикл 2 (15–28 сент):** RQ3 на rel-f1/rel-event/rel-stack (плотности,
  канарейка, стратегии); текст статьи; внутренняя рецензия по чек-листу
  2607.04958.
- **29 сент – 2 окт:** полировка, анонимизация артефакта, подача.
- Scope-нож (если горит): адверсариальная стратегия RQ3 → future work; holdout-

  известными нарушениями.

## 9. Риски

- Double-blind: публичные репо/демо → анонимизированная копия артефакта, ссылки
  как «prior demo» по правилам FSE.
- ICDM-демо на рецензии: вклады не пересекаются (там метод+факт, тут
  zero-config + цикл), проговорить при подаче.
- Сквозное согласие вердиктов может просесть из-за двух известных промахов карты —
  тогда human-review очередь для класса «дата-не-канал» описывается как фича
  инструмента, не как отказ (порог §6 это уже предусматривает).
