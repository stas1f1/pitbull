# PITBULL — финальный план подачи (FSE 2027, research track)

Статус: **ревизия 5, финальная** (3 сентября 2026, ночь) — по четвёртой критике
(`critique/fse2027_rev4.md`; предыдущие: `fse2027_pitbull_proposal.md`,
`fse2027_rev2.md`, `fse2027_rev3.md`). Правки: TravisTorrent понижен из яруса B
в Discussion (пакет оказался плоскими таблицами без timestamp'ов — валидация
карты на нём не строится, см. §5), правило невозмущаемых каналов уточнено и
сужено, две категории пар истины в RQ2а. **Правило ярусов: после 3 сентября в
A и B ничего не добавляется, только убирается. Дальше — прогоны, не ревизии.**
Пороги §8: заморожены 2 сентября; датированные добавления 3 сентября — до
старта полных прогонов. Дедлайн full paper: **2 октября 2026** (решение
22 января 2027, Major Revision 5 марта 2027). ~11 стр., double-blind.

Терминология: witness — расхождение выходов прогонов на полной и усечённой
базе; canary-прогон — прогон на копии, где возмущено всё, что усечение делает
недоступным, **возмущением по типу данных**: числа — сдвиг, даты — сдвиг за
горизонт данных, категории и строки — sentinel-значение вне словаря, ключи не
трогаются. Правило для колонок-каналов (уточнено рев. 5): канал, чья
собственная доступность равна его значению (дата доставки известна в дату
доставки), возмущается любым значением > t — множество недоступного при этом
не меняется и D'|t = D|t сохраняется; не возмущаются только каналы, чьё
значение ≤ t управляет доступностью ДРУГИХ колонок с avail > t — их короткий
список публикуется как реальное слепое пятно canary, закрытое усечением. Held-out моменты — моменты проверки, не участвовавшие в
вынесении вердикта. Общее определение: выход программы должен быть функцией
только от D|t; усечение проверяет φ(D,t) = φ(D|t,t), canary — φ(D,t) = φ(D',t)
для D' с D'|t = D|t.

## 1. Центральный тезис

Дифференциальная проверка point-in-time корректности требует человека в
четырёх местах: объявить карту доступности, написать адаптер, дать корректную
реализацию-эталон, выбрать моменты проверки. Эталон не нужен для вердикта —
его заменяет инвариант; в плане он используется только для оценки подлинности
исправлений (одна фраза в статье). Статья устраняет ещё два шага и честно
называет последний:

> **Цикл дифференциальной проверки кода признаков замыкается без ручной
> подготовки:** карта доступности выводится из схемы и данных, два разнесённых
> момента дают детекцию ~100% для доминирующего класса утечек, и цикл
> «witness → исправление → верификация на held-out моментах» доводит N из M
> протекающих программ до чистых (детекция ~100% — в наших наборах; второе
> условие — ярус C). Без чекера модель собственную утечку не
> находит и не чинит: 1/12, и тот успех — удалением признаков. Остающийся
> ручной шаг — интерфейс программы (§6) — назван и измерен воронкой.

Главное число первой страницы — абсолютный исход RQ0 (N/M на held-out
моментах) **с явным указанием уровня карты, под которым он получен**
(per-table / per-column, §4 RQ0); согласие с ручной картой — валидация, второй
строкой. Фразы про детекцию и про исправление не смешиваются: 1/12 — про
исправление без называния класса ошибки; способность LLM к детекции измеряется
отдельно (RQ2а) и заявляется по фактически прогнанной ступени.

Заголовок: «PITBULL: Closing the Loop — Zero-Configuration Point-in-Time
Testing and Repair of Generated Feature Code»; рецензионная версия — без имени
(решение 3 сент: проект остаётся PITBULL, в рукописи плейсхолдер, возврат в
camera-ready). В abstract одной фразой: «zero-configuration — for programs in
the harness interface; wrapping real pipelines is the remaining manual step,
measured in §X». Анонимизация — единый проход по тексту, метаданным PDF и
артефакту, **с исключением библиографии** (цитата демо обязана остаться в
третьем лице по правилам FSE); проверка — пункт чек-листа подачи.

Опора односторонности (предпосылка в Approach, не вклад): для произвольного
чёрного ящика доказать отсутствие утечки невозможно; Fonseca (TOSEM 2026) —
свойство «утечки нет» не перечислимо уже при доступности, зависящей от
значений. Формулировка: «никакой метод общего назначения не доказывает
отсутствие; дифференциальный тест полон по свидетельствам»; «оптимален» не
употребляется. Его future work №2 — вывод структуры доступности из реальных
фреймворков — наш RQ1. Его набор специально сконструированных утечек — 
доказательство существования, не частоты.

## 4. Research questions

**RQ0 (главный). Даёт ли полный цикл под автоматически выведенной картой те же
исходы, что под ручной?** Определение метрики: **M — число программ,
протекающих под ручной картой; программа, которую цикл под авто-картой молча
не увидел, считается провалом цикла, а не выпадает из знаменателя.** Основная
единица наблюдения — программа (при плотности 0.94–1.00 пары
программа×момент — одна ошибка карты, посчитанная двадцать раз); пары —
вторичная отчётность. Направление расхождений: LEAK→CLEAN — пропуск,
CLEAN→LEAK — ложная тревога. Для режима «очередь ручной проверки» — 
операционное число: сколько таблиц на базу попадает в очередь (это стоимость
инструмента в глазах рецензента). RQ0 оформлен перезапускаемым скриптом:
после яруса B прогоняется заново под per-column картой, обе версии — в статью
с указанием уровня.

**RQ1. Какую часть карты можно вывести там, где её никто не объявил?**
Как в ревизии 3: тривиальность 25/34 признана, ценность — Olist, per-column,
колонки без канала; baselines — метаданные, v0, LLM-карта;
пре-регистрированный исход «LLM-карта не хуже» → вклад переформулируется в
проверяемость карты циклом; каппа Коэна; ручная per-column разметка RelBench —
два аннотатора (§9). Внешняя валидация на чужой разметке — ярус B (§3).

**RQ2а. Находит ли LLM утечку чтением кода?** Метрики против вердикта чекера И
против известной истины. **Две категории пар, не смешиваются (рев. 5):**
(1) пары с рукописной правильной программой — истина по построению, сейчас ~6
(задачи A/B/C Olist, адаптеры olist/f1, featuretools): precision на них —
иллюстрация, число честно называется; (2) пары «протекающая / исправленная и
верифицированная» — это метка чекера, НЕ истина по построению (иначе
циркулярность возвращается через чёрный ход): на них отчитывается согласие с
чекером, не precision. **Порог применяется к самой сильной
фактически прогнанной ступени** (в ярусе A это F1): recall ≥ recall чекера −
0.1 И ложные срабатывания на чистых ≤ 0.1 → тезис «незаменим как детектор»
сужается до «верификатор + локализатор». Intro пишется так, чтобы пережить оба
исхода. Строка таблицы: чего нет у LLM-вердикта при любом recall.

**RQ2б. Что именно исправляет цикл?** Разметка механизма до матрицы — чтением
кода (witness даёт колонки-каналы, но «нет фильтра / не тот timestamp /
сконструированный агрегат» различимы только по коду; дёшево, но вручную);
CLEAN@k по механизмам; если механизм один — число публикуется как ограничение.
Матрица, статистика, held-out, повтор при no_code — как в ревизии 3;
CI — кластерный бутстрап по программам, Мак-Немар вторично.

**RQ3. Сколько моментов нужно, что они стоят, что ловит каждый уровень?**
Baseline «тестовый момент бенчмарка» (rel-event 23/24); плотность и кривая
детекции. Canary: типовое возмущение (шапка), два контроль-случая (§3, ярус A),
доля ложных срабатываний с допуском, перекалиброванным под возмущение.
**Правило трёх — по программам, не по парам:** 20 моментов одной чистой
программы — не 20 независимых испытаний (её ложная тревога воспроизведётся на
большинстве моментов); эффективный n — число чистых программ (~30), честная
граница — порядка 10%, и формулировка «полное предупреждение» привязывается к
границе по программам; граница по парам — вторичная. Таблица стоимости: ярус A
— Olist + rel-f1; rel-amazon — ярус B.

Как в ревизии 3 (61 протекающая генерация с разметкой механизма; 2 агентных;

инфляции; их ручной аудит — то, что мы автоматизируем) и абзац в Discussion
(ярус C): согласие классификации колонок LLM-картой по словарю данных с их

валидацией карты.
