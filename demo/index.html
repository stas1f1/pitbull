Did the feature peek?

A two-run test that catches machine-learning features built from information that did not exist yet, and the five places we found them: a popular library's defaults, our own code, published expert SQL, code written by language models, and SQL written by an autonomous agent.

ITMO University · ICDM 2026 demo track · all data computed from real public databases

In one breath

When you predict something about a customer or a seller as of a date, the features are usually aggregates: average review so far, orders in the last month. They must only use what was known on that date, because in training the database already holds what happened afterwards and in production it does not; an aggregate that reads later data looks good offline and differs from what the model will see in use. In databases with several tables that rule is easy to break without noticing: a review is attached to an order, but written weeks later, and an “average review” computed as of the order date quietly includes it. We run the feature code twice, once on the whole database and once on a copy with everything after the date physically removed, and compare. If the numbers differ, the code peeked. No parsing, no guessing. Feature code is increasingly written by AutoML libraries and coding agents instead of a person you can ask, which makes a check that works on the running program, without reading it, the natural gate.

The orders were placed before the date, so they pass a filter like order_date <= date. Their reviews had not been written yet. A feature that averages review scores over “orders so far” quietly includes complaints that arrive later, and the model learns from them. In this database a review comes a median of 10 days after the order (90% within 23, the slowest 147); on 1 April 2018 about 5% of past orders had a review still to come. Delivery dates behave the same way.

2The check: run it twice

Take any feature program: a library call, an agent's output, a colleague's script. We do not read it. We run it on the full database, then on a copy where every row and every value dated after the seed date has been deleted, and compare the two outputs. Same program, less information, different answer ⇒ it used the future.

Why not just always run on the past-only copy? With one seed date per call, that is a fix.
  But real training tables have a different date on every row, so the program itself has to cut per row; that is what the check verifies.
  And a program that peeks is a defect worth reporting; masking it once leaves it in the code.

The same trap in the wild

  

    
code written by language models

      
We asked two code models, deepseek-v4-flash and bytedance-seed/seed-2.0-code, for feature functions for one of our tasks, giving them the schema and nothing about leakage.
      Of the generations that ran, 62% from the first and 22% from the second peeked, every case we examined in the same way as average_review above:
      filter the orders by order date, ignore the review date. About half the generations crash before producing a table at all, so the honest read is a range: between 26% and 70% of everything the two models wrote.
      Warning the model in the prompt lowered the pooled rate from 46% to 41% to 15%, never to zero;
      on a task with no second time axis both models produced zero violations. When an agent writes features nobody reads, this is the failure mode to expect.

    
published expert SQL

      
We also executed the hand-written feature SQL of the RelBench user study against its public databases.
      Fourteen of fifteen files run; eight diverge, through future rows of a race schedule, through frequency tables computed over the whole history, and through joins to people who had not signed up yet.
      A careful manual audit of the same corpus had found two violations, and had cleared two of the files the check flags. Section 7 has every verdict.

  







  
4What a peek costs

  
The damage is optimism: the model looks better offline than it will be in use. Move the cutoff δ days into the future and watch the AUC of one fixed model climb.
  A month's error is worth 6–12 points here; no cutoff at all, up to 27.

The same defect can be cheap or expensive depending on what is being predicted. Our own leaky code (reviews and delivery dates read too early)
  inflated AUC by 3–5 points when the target was review quality, and by 0.2 points when the target was seller activity. Same code, same leak, a twenty-fold difference in damage.
  So the score cannot tell you whether the features peek; the check has to run either way.







  
5The blind spot of the usual test

  
Commercial AutoML tools look for leakage by asking: does any single feature predict the target suspiciously well?

The two grey bands are the two tasks, and the gap between them is the point. On task B even a two-month shift barely clears 0.8;
  on task A the honest strongest feature (“days since last order”) scores 0.83–0.86 on correct code (the green dots), because recency genuinely predicts churn.
  So a threshold low enough to catch B's leaks flags A's clean pipeline. Leaks that spread across many aggregate features are worse still:
  the featuretools run is inflated by 16 points while its best single feature scores 0.81, and the join-only leak (red) does not move the probe at all. Move the slider: no position separates leaky from clean.







  
6Where exactly it leaks

  
The database has a short list of ways the future can enter: rows of a table that appear after the date, and values of a column that become known after the date. We call each one a channel.
  Delete one channel at a time, re-run, and see which output columns move.

  

  

  
Deleting exactly the channels found and re-running gives a clean result, which confirms nothing else contributed. This locates the defect; it does not repair it, because any program looks clean on a pre-cut input.
  The repair is in the code (compare the two versions of our reference code in section 2: the fix is two lines).

The defect shows up on 23 of the 24 dates, on some of them for half the rows.
      On one date it shows up nowhere, and that is the date the benchmark scores on. Test only there and the file looks clean.
      So a clean verdict says the code did not peek on the dates you tried, and nothing more.
      Pick dates from the middle of the training period; the date the score is reported on is the least sensitive one.


      
Writing “on or before the date” where “before” was meant

      
The cutoff is one comparison in the code: keep the rows dated <= the date, or the rows dated
      < the date. Get it wrong and rows stamped exactly on the date slip in.
      Formula 1 race results show what that is worth. Races before 2005 are stamped with the day only, so a race
      held on the date is stamped with the date itself and walks straight into its own features. From 2005 on races
      carry the start time, which is never exactly midnight, so nothing slips in and the same mistake costs nothing.

      

      
Same code, same task, same database; the only difference is
      <= instead of <. The timestamps decide whether it costs
      anything. That is why the code has to be run; reading it cannot settle this.


    

  







  
8What it cannot do

  

    
It proves peeking; it cannot prove there is none
A peek that made no difference on the tested date is not seen on that date. Zero divergence on the dates we test makes peeking unlikely but cannot rule it out.

      
Some columns are undecidable
A status field that gets overwritten with no history (“cancelled”) has no timestamp for when it changed. The past-only copy looks identical to the full one, so no execution-based test can decide it. We drop such columns instead of calling them clean.

    
It trusts the availability map
Somebody has to say which column dates each value: the review is known at review_creation_date, the delivery at delivered_customer_date. If that map is wrong, the check tests the wrong thing. Today the map is a short hand-written declaration.

      
Narrow where it counts
Costs in AUC come from two databases and four tasks; the verdicts in section 7 cover five more databases but carry no cost measurement. The language-model rates are two models on one task with wide intervals; read them as “this happens” and nothing more precise. And what we measure is how much a peek inflates the offline score; the extra loss when a model trained on peeking features is served on data where the future does not exist yet is a separate effect we did not measure.
