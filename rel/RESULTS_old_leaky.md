# Утечки во времени в многотабличных признаках: три задачи

*Данные: Olist, реальный бразильский маркетплейс. 7 таблиц, 112 650 позиций заказов, 3 095 продавцов, 32 951 товар, сентябрь 2016 — октябрь 2018. Задачи построены в стиле RelBench: сущность + момент предсказания + горизонт 90 дней. Три момента предсказания (январь, апрель, июль 2018), обучение на всех предшествующих. Модель — LightGBM. Всё на 2 ядрах CPU, без GPU.*

«Проверка» — стандартная промышленная эвристика «максимальный AUC одного признака». Пороги: DataRobot 0.85 предупреждение / 0.975 автовыброс; H2O Driverless AI 0.8 / 0.95 / 0.999.

## Задачи

**A. Активность продавца.** Для каждого продавца, активного за 180 дней до момента T, предсказать, будет ли у него хоть один заказ в следующие 90 дней. Цель напрямую связана с давностью последнего заказа.

**B. Качество продавца.** Для тех же продавцов предсказать, будет ли средняя оценка отзывов за следующие 90 дней ниже 4 (нужно ≥3 отзыва в окне). Цель **не** связана с давностью — поэтому утечка не тавтологична. Задача честно тяжёлая: базовый AUC 0.57–0.60.

**C. Спрос на товар.** Для каждого товара с ≥2 заказами за 180 дней до T предсказать, будет ли он заказан в следующие 90 дней. Признаки разделены на две группы:
- собственная история товара;
- агрегаты по всей истории **продавца**, к которому привязан товар, — то есть признаки, полученные по пути соединения `товар → позиция заказа → продавец → вся история продавца`.

Разделение позволяет включать утечку в каждой группе отдельно.

## Что получилось

### 1. Величина эффекта — от 8 до 26 пунктов

Сдвиг временной отсечки на 30 дней (типичная ошибка: взяли границу календарного месяца вместо момента предсказания) даёт **+7…+11 п.п.** на задачах A и B. Полное отсутствие отсечки — **+12…+26 п.п.**

Эффект устойчив по всем трём моментам предсказания. Для сравнения: весь эффект неправильного отбора модели на одной таблице был **0.4 п.п.**

Самый показательный случай — задача B: модель уезжает с 0.59 на 0.78. Из «практически не работает» в «выглядит готовой к внедрению».

### 2. Существующие детекторы слепы ровно там, где интереснее всего

**Задача B: ни один режим не переходит ни один порог.** Даже полное отсутствие отсечки даёт максимум 0.832 — ниже порога предупреждения DataRobot (0.85) и сильно ниже порога H2O (0.95). Причина: когда цель не сводится к давности, утечка не собирается в одну колонку, а размазывается по всему набору агрегатов. Одномерная проверка этого по построению не видит.

**Задача C2 — самый чистый результат.** Утечка приходит через соседнюю сущность по пути соединения. Максимальный AUC одного признака: **0.714 / 0.722 / 0.717 при корректной отсечке и ровно 0.714 / 0.722 / 0.717 при утечке.** Значение не меняется ни на тысячную. Практик, прогнавший DataRobot или H2O, получит полностью чистое заключение — и внедрит модель, офлайн-оценка которой завышена на 3–4 пункта.

**Задача A — обратная проблема.** Там проверка утечку ловит (0.93–1.00 против 0.83–0.86), но корректный пайплайн сам даёт 0.833–0.861 и задевает порог 0.85. То есть проверка ложно срабатывает на правильном коде: `days_since_last` **законно** является сильнейшим признаком в задаче про отток.

### 3. Отсюда — почему нужен агент, а не список проверок

Различие между корректным и утёкшим вариантом лежит не в значениях признаков, а в том, **по какому окну посчитан агрегат и по какому пути соединения он собран**. Это свойство способа построения, а не данных.

- В задаче A статистика признака одинаково высокая в обоих случаях — потому что признак законно силён.
- В задачах B и C2 статистика одинаково низкая в обоих случаях — потому что утечка размазана.

В обе стороны одномерный тест бесполезен. Проверить можно, только прочитав код или SQL построения признака и сверив границу окна с моментом предсказания. Перечислить такие проверки заранее нельзя: они зависят от конкретной схемы, набора путей соединения и функций агрегации.

## Оговорки

- Одна база данных, три задачи, три момента предсказания. Предварительный результат.
- Не сам RelBench — `relbench.stanford.edu` и HuggingFace недоступны из этой сети. Структура задач воспроизведена по описанию RelBench (сущность, момент предсказания, горизонт, временная фильтрация).
- Режим «окно шире на 90 дней» в первом прогоне давал ровно 1.000 — вырожденный случай, окно совпало с горизонтом метки. В итоговых таблицах он не используется.
- Базовый AUC задачи B низкий (0.57–0.60). Это не недостаток, а свойство задачи: именно на тяжёлых задачах утечка наиболее соблазнительна, потому что превращает бесполезную модель в убедительную.
