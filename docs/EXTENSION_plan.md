# Расширение на новые базы — план

Цель: добавить к Olist одну-две базы с тем же набором экспериментов.

**Работа идёт на локальной машине**, где сеть не ограничена. Поэтому первый шаг — не выбор
баз, а проверка того, что реально скачивается. Выбирать эксперименты имеет смысл только
после этого.

## 2. Что делает базу пригодной

### Технические требования — без них база бесполезна

1. **≥3 таблицы со связями по ключам** и метка времени появления строки в событийных.
2. **Побочная временная ось** — колонка, которая дописывается к строке позже её появления
   и имеет собственную метку: отзыв к заказу, факт доставки, исход заявки, результат гонки.
   Без неё база не проверяет то утверждение, ради которого всё делается.
3. **История, достаточная для ≥3 моментов предсказания** с горизонтом и обучающими
   моментами до них.
4. Желательно **изменяемое поле без истории** (статус) — идёт в ограничения как
   непроверяемый класс.

### Что делает базу интересной

Ценность бывает трёх видов, и две однотипные базы дают только первую трижды.

| | что даёт |
|---|---|
| **V1 репликация** | тот же эффект на другой схеме → снимает возражение «одна база» |
| **V2 новый механизм** | то, что Olist проверить не мог в принципе |
| **V3 чужой код** | прогон оракула по коду, который писали не мы |

## 3. Кандидаты, по убыванию интереса

**rel-stack — единственный источник V3.** По ней у нас уже лежит чужой код: 15 файлов
экспертного SQL из `snap-stanford/relbench-user-study` (там мы статически нашли нарушение
`stack/user-badge :: badge_freqs`) и 37 уникальных SQL из корпуса RelAgent для задачи
`user-engagement`. Сейчас оба результата помечены в статье как статический разбор, а не
исполнение — это ограничение №20. С данными мы прогоняем по ним дифференциальное
исполнение и превращаем ограничение в результат. Схема принципиально иная (форум, не
магазин), побочная ось богатая: голоса, комментарии и значки приходят к посту намного
позже его создания; `Posts.Score` и `AcceptedAnswerId` — изменяемые поля.

**Home Credit 2024 — единственный источник V2.** Даёт две вещи, которых у Olist нет:

- **дневная гранулярность дат.** На Olist ошибка на единицу (`include_cutoff_time`) дала
  ровно 0.00, потому что события имеют секундную точность, а моменты стоят в полночь.
  Мы записали «эта ошибка опасна на дневной гранулярности» и проверить не смогли.
  Здесь `date_decision` и все глубинные таблицы в днях;
- **глубина соединения 2 и больше.** У Olist путь ровно в один шаг (товар → продавец).

Задача и метка заданы авторами соревнования — не надо изобретать постановку и отбиваться
от «вы придумали задачу под свой результат». База большая, нужна подвыборка.

**rel-f1 / Ergast — гарантированный вариант, V1 плюс частично V2.** Даты в `races.date`
**дневные**, и момент предсказания, поставленный на день гонки, включает результаты этой
самой гонки — то есть ошибка на единицу проверяется и здесь. Путь соединения есть
(гонщик → команда). Плюс у нас лежат три экспертных `feats.sql` для задач `driver-dnf`,
`driver-position`, `driver-top3` — то есть частично доступен и V3. Минус: сущностей
на момент мало (порядка 20–40 гонщиков), AUC шумный, нужно много моментов предсказания.

**rel-hm, rel-amazon — чистая репликация.** Минимальный риск, задачи определены RelBench.
Брать, если rel-stack и Home Credit не поднялись.

**Не брать:** AdventureWorks, Sakila, Northwind — учебные синтетические базы, аргумент
«мы ничего не конструировали» на них ломается. MovieLens — побочная ось слишком слабая.
BPI 2017/2019 интересны внешней разметкой (пары «протекающий и починенный» из
BPM 2021 Workshops), но событийные логи требуют слоя преобразования — это следующий заход.

## 4. Инфраструктура готова: на новую базу нужен один файл

| файл | что |
|---|---|
| `rel/dsapi.py` | `TemporalDB` с отношением доступности, `TaskSpec`, `DatasetAdapter` |
| `rel/suite.py` | весь набор ячеек для любого адаптера: `python3 suite.py <имя>` |
| `rel/gate.py` | ворота приёмки, около минуты: `python3 gate.py <имя>` |
| `rel/adapters/olist.py` | эталонный адаптер |
| `rel/adapters/_template.py` | шаблон, пять мест для заполнения |

Обобщённый набор воспроизводит **36 из 36** опубликованных значений Olist знак в знак
(`rel/out/olist_auc.csv` против `rel/fix_ab_auc.csv` и `rel/fix_c.csv`). Старые скрипты
не тронуты, добавление аддитивное.

### Ворота приёмки — обязательны до любых экспериментов

`python3 gate.py <адаптер>` проверяет и печатает вердикт:

1. объём (≥20 тыс. строк в основной таблице);
2. побочная временная ось: есть ли и каков лаг — медиана, p90, максимум, доля строк с лагом;
3. непроверяемые колонки (изменяемые поля без истории);
4. размер и баланс задач на каждом моменте;
5. **наивная программа протекает, PIT-корректная — нет.** Если PIT-версия сама протекает,
   адаптер сломан; если наивная не протекает, показывать нечего.

Правило выведено из провала: на Olist наш «корректный» эталон протекал, и мы узнали об
этом через неделю. Ворота ловят такое за минуту.

## 5. Набор ячеек — ровно тот же, что на Olist

Одинаковый набор признаков во всех режимах, меняется только временная семантика.

| режим | что | зачем |
|---|---|---|
| `pit` | корректная отсечка по отношению доступности | база отсчёта |
| `naive` | фильтр по времени строки, колонки берутся целиком | дефолтный способ ошибиться |
| `delta5`…`delta90` | сдвиг на 5, 10, 15, 20, 30, 45, 60, 90 дней | кривая `I(δ)` |
| `nocut` | отсечки нет | верхняя граница |
| `join_only` | утечка **только** через путь соединения | самый ценный: проверка не меняется |
| `own_only` | утечка только в собственной истории | контраст |
| `naive_nbr` | наивный режим только у соседа | разделение вкладов |

В каждой ячейке: AUC фиксированной модели (LightGBM, те же параметры, seed 0),
промышленная проверка «максимальный AUC одного признака» с именем сильнейшего признака,
завышение относительно `pit`. Отдельно — дифференциальное исполнение: наивная и
PIT-программа × каждый момент, вердикт, список расходящихся колонок, число расхождений.

**Дополнительно, если база позволяет:**

- **дневная гранулярность** (Home Credit, rel-f1): ячейка `inclusive` против `exclusive`
  границы. На Olist она была вырожденной, здесь это новый результат;
- **чужой SQL** (rel-stack, частично rel-f1): прогон оракула по `audit/*.sql` и по
  37 запросам RelAgent из `p2_out/unique_queries.json`. Самый ценный отдельный результат
  всего расширения.

## 6. Предзарегистрированные критерии

Зафиксировать до прогона, задним числом не толковать.

| Что | Подтверждение | Что означает провал |
|---|---|---|
| Репликация величины | `naive` даёт ≥1 п.п. хотя бы на одной задаче базы | эффект специфичен для Olist — писать первой строкой |
| Слепота проверки | хотя бы на одной задаче проверка < 0.85 при подтверждённом нарушении | слепота специфична для Olist |
| Утечка через соединение | `join_only` ≥1 п.п. при изменении проверки < 0.01 | механизм не переносится |
| Оракул | `pit` даёт ЧИСТО на всех моментах | адаптер протекает — чинить, не публиковать |
| Ошибка на единицу | ≥1 п.п. на дневной гранулярности | гипотеза о гранулярности неверна, честно снять |
| Оракул по чужому SQL | вердикты совпадают с ручным аудитом на ≥12 из 15 файлов | либо баг оракула, либо ошибка аудита — разбирать поимённо |

**Отрицательный контроль обязателен на каждой новой базе:** момент предсказания в максимум
временных меток, ожидание — ноль срабатываний, запускать **до** основных измерений.
На Olist именно он поймал баг оракула.

Одно правило поверх всего: **числа замораживаются раньше, чем начинается вёрстка**.
Одна база с честным ограничением проходит рецензирование, три базы с опечаткой в таблице — нет.

## 8. Промпт для локального агента

> Контекст: `HANDOVER.md` — состояние проекта, `docs/EXTENSION_plan.md` — этот план,
> `rel/adapters/_template.py` — шаблон адаптера, `rel/adapters/olist.py` — эталон.
>
> Шаг ноль: проверить, что скачивается, по таблице §1, и записать результат. Ничего не
> проектировать, пока это не сделано. На проверку не больше трёх часов.
>
> Дальше: выбрать базы по §2 и §3, написать адаптеры, прогнать `gate.py`, и только после
> пройденных ворот — `suite.py`. Отрицательный контроль на каждой базе **до** основных
> измерений.
>
> Правила: набор признаков одинаков во всех режимах, меняется только временная семантика;
> итоговая модель одна и та же везде, seed фиксирован; критерии из §6 зафиксированы заранее
> и задним числом не толкуются; подвыборки фиксируются seed-ом и документируются.
>
> Не делай: не меняй `rel/fix_*.py` и `rel/RESULTS.md` — там опубликованные числа Olist;
> не сравнивай абсолютные AUC между базами; не подгоняй постановку задачи под желаемый
> результат — если завышение около нуля, так и напиши.
>
> Если результат противоречит гипотезе — первой строкой раздела.
>
> На выходе: `rel/out/<база>_auc.csv`, `_oracle.csv`, `_summary.md` и `EXTENSION_RESULTS.md`
> с числами, вердиктом по каждому критерию §6 и разделом «что осталось непроверенным».
