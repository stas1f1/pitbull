# План: цикл починки как переиспользуемый скилл — сборка, валидация, сведение в таблицу

Инструкция для агента, который будет это исполнять. Не является частью
`docs/PLAN.md` — это отдельный, предлагаемый на подтверждение довесок к плану
(см. §7 «Что сделать с `docs/PLAN.md`» в конце).

---

## 0. Обязательное предусловие

Всё, что ниже требует вызовов LLM через OpenRouter (`z-ai/glm-5.3-flash`).

**Дисциплина безопасности A2, обязательна и здесь** (см.
`docs/experiments/a2-rq0-olist.md`, раздел «Метод»): сетевой этап (получение
ответа модели) и этап исполнения сгенерированного кода — разные процессы;
перед исполнением непроверенного кода переменная `OPENROUTER_API_KEY`
удаляется из окружения. Скилл почти по определению исполняет код, который сам
же и сгенерировала LLM, — обходить это разделение нельзя.

## 1. Текущее состояние (то, с чем сравниваем)

Все числа — из `docs/experiments/a2-rq0-olist.md`, `a3-rq2a-llm-detection.md`,
`a4-rq2b-repeated-repair.md`, `a5-rq3-density-cost.md` (статус всех четырёх —
`in_review`, положительные/смешанные вердикты, не переоткрывать заново, если
не найдётся конкретная методологическая причина).

| Эксперимент | Модель | Корпус | Результат |
|---|---|---|---|
| A2 — RQ0, полный цикл, ручная карта | `z-ai/glm-5.3-flash`, F1, до 5 итераций | M=76 (62 из A1 + 14 canary-only) | CLEAN@5 = 75/76 = 98.7%, порог §8 (≥0.9) пройден на CLEAN@2 |
| A4 — RQ2б, воспроизводимость | тот же, 3 независимых повтора | 62 программы × 3 = 186 | CLEAN@5 = 182/186 = 97.8%, cluster bootstrap 95% CI [95.2%, 100%] |
| A3 — RQ2а, детекция чтением кода | тот же, F0/F1 | 75 checker-пар + 6 рукописных | F1: recall 97.3% (порог ≥90% пройден), FPR 12.0% (порог ≤10% НЕ пройден) — вердикт `neutral` |
| A5 — RQ3, плотность/canary FPR | без LLM | 62 LEAK + 30 CLEAN | k=2 моментов ≈ насыщение; witness FPR 0/30; **canary FPR 4/30 = 13.3%** — не самостоятельный вердикт |

Прогон починки идёт по промпту F1 (`pilot/a2_full_fetch.py`, переменная
`F1_TEXT`, дословно):

```
В коде выше может быть утечка данных из будущего. Требование: признаки
для момента seed_time должны вычисляться ТОЛЬКО по информации, которая уже существует
на момент seed_time. Учитывай, что события в базе появляются в разное время: например,
отзыв на заказ пишется позже самой покупки, а даты доставки заполняются после неё.
Проверь свой код на это требование и верни исправленную версию функции get_features
(та же сигнатура), в одном блоке ```python ...```, без пояснений.
```

— добавляется к `H.NEUTRAL_PROMPT` (постановка задачи + текущий код) из
`prestudy/p3_baseline_run.py`. Верификация — `oracle.truncate` +
`oracle.frames_equal` + `oracle.perturb_canary` (модуль `prestudy/oracle.py`,
включает фикс `pandas.Categorical` из коммита `e4a8fa4`) на диагностических
моментах `2018-01-01, 2018-04-01, 2018-07-01` и held-out
`2017-10-01, 2018-02-01, 2018-06-01`. Программа «чистая», только если оба
уровня молчат на всех шести.

**Известные острые случаи, которые нельзя усреднить и забыть:**

1. `deepseek-v4-flash-0731#79` (UID `f1cade690ca333e8`, из A2) — после 5
   итераций F1 witness молчит, но canary стабильно ловит `delivered_recency_days`
   на всех шести моментах. Это единственный финальный провал A2. Если скилл
   на этой же программе провалится тем же образом — это подтверждение
   паритета, не новый дефект.
2. Три канала, на которых LLM-детектор (A3, режим F1) расходится с ручной
   картой чекера: изменяемый `order_status` (4 случая), задержанная
   доступность платежа (3), `review_answer_timestamp` вместо принятого картой
   `review_creation_date` (2). Если скилл (в роли починщика, не детектора)
   будет спорить с чекером именно на этих каналах — это ожидаемо, не повод
   считать скилл неисправным.
3. Canary даёт 13.3% ложных срабатываний на CLEAN-программах (A5) — скилл не
   должен трактовать одно срабатывание canary как безусловный провал без
   учёта этой базовой частоты.

## 2. Что строим

**Скилл-кандидат (рабочее имя `pit-repair`, можно переименовать):** пакет
`.claude/skills/pit-repair/SKILL.md` (+ вспомогательные файлы при
необходимости), который агент может вызвать на произвольной функции вида
`get_features(db, entity_ids, seed_time)` (интерфейс §6 плана) и получить:
детекцию через дифференциальное исполнение (witness+canary), и если найдена
утечка — до 5 итераций «починка по F1-обратной связи → повторная проверка»,
с финальным вердиктом и историей итераций в том же составе полей, что
`pilot/a2_full_manifest.json` (`clean`, `iters_used`, история по итерациям).

Это НЕ новый метод — это переупаковка уже провалидированного цикла
(`oracle.py` + `F1_TEXT` + логика из `pilot/a2_full_fetch.py`/
`a2_full_validate.py`) в форму, которую использует произвольный агент, а не
только наш закрытый pilot-скрипт.

### 2.1 Собрать скилл

1. Вызвать `skill-creator` (доступен в этой среде) для правильной упаковки
   `SKILL.md` — не изобретать формат вручную.
   **Если `skill-creator` недоступен** в среде, где исполняется этот план
   (другой инстанс, другой набор скиллов) — не угадывать схему с нуля.
   Взять минимальный консервативный референс — `.claude/commands/continue.md`
   в этом же репозитории (YAML frontmatter с `description` + тело инструкции)
   — и оформить `.claude/skills/pit-repair/SKILL.md` по той же логике
   (frontmatter с `name`/`description` + тело). В отчёте
   (`docs/experiments/d1-skill-repair-parity.md`) явно указать, что упаковка
   сделана вручную, без проверки официальным инструментом — как ограничение,
   а не скрытая деталь.
2. Внутрь заложить:
   - описание задачи и интерфейса (§6 плана: `get_features(db, entity_ids, seed_time)`,
     обёртке разрешена перестановка вызовов, запрещена логика признаков);
   - шаг детекции: вызвать дифференциальное исполнение (`oracle.truncate`,
     `oracle.frames_equal`, `oracle.perturb_canary`) на моментах, которые
     передаёт вызывающий (или на дефолтном наборе из шести моментов A2, если
     не передано);
   - шаг починки: если найдена утечка — тот же текст `F1_TEXT` (дословно,
     без пересказа);
   - шаг повторной проверки: те же три функции `oracle.py` на held-out
     моментах, отдельных от диагностических;
   - до 5 итераций, останов при первом CLEAN;
   - явное упоминание трёх спорных каналов и 13.3%-й базовой частоты canary
     из §1 выше — не как догма, а как контекст для агента, если он должен
     объяснить пользователю расхождение.
3. Зафиксировать в самом скилле дисциплину безопасности из §0 (сеть/исполнение
   раздельно) — если скилл сам оркестрирует вызов модели и исполнение кода.

### 2.2 Что не делаем на этом шаге

- Не тестируем другие модели, кроме `z-ai/glm-5.3-flash` — это отдельный,
  более дешёвый прогон уже посчитан (A2 — $0.1228, A4 — $0.201504), смена
  модели меняла бы две переменные одновременно (упаковка и модель) и сломала
  бы парную сравнимость.

## 3. Валидационный прогон — тот же корпус, та же модель

**Корпус:** ровно тот же M=76, что в A2 — 62 программы из подтверждённой
A1-разметки + 14 canary-only, идентифицируемые 16-символьным префиксом
SHA-256 кода (`program_uid`), как в `pilot/a2_full_manifest.json`. Взять
исходный (протекающий) код каждой программы из этого манифеста — не
регенерировать заново.

**Модель:** `z-ai/glm-5.3-flash`, temperature 0.2, max_tokens 14000,
`reasoning.max_tokens=1500` — те же параметры, что в
`pilot/a2_full_fetch.py`.

Как запускать — [OpenHarness](https://github.com/HKUDS/OpenHarness) —
отдельный от Claude Code агентный фреймворк с собственной подсистемой
`skills/`, которая по README проекта заявлена совместимой с форматом
`anthropics/skills` («OpenHarness remains compatible with anthropics/skills
and claude-code plugins»), и поддерживает как Anthropic-, так и
OpenAI-совместимые провайдеры, включая GLM- и DeepSeek-семейства — то есть в
принципе те же модели, что в A2–A5. Ключевое методологическое требование
прогона: модель должна дойти до починки через реальный вызов скилла в
харнессе OpenHarness (сама решает использовать `pit-repair`, харнесс подгружает
`SKILL.md`), а не через ручную сборку того же промпта в питоне — иначе
проверка вырождается в A2, просто пересчитанный другим скриптом.

Прежде чем считать это готовым методом, а не предположением с моей стороны
(вывод сделан по одному прогону README через `WebFetch`, не по полному чтению
документации проекта), исполняющему агенту нужно на месте проверить:

1. **Формат/путь skills у OpenHarness** — совпадает ли его ожидаемая структура
   с `.claude/skills/<name>/SKILL.md` буквально, или у него свой каталог
   (`skills/` по описанию архитектуры) и скилл нужно туда скопировать/
   симлинкнуть. Не считать совместимость нулевого трения гарантированной
   только из-за фразы в README.
2. **Через какой эндпоинт OpenHarness реально вызывает `z-ai/glm-5.3-flash`** —
   через OpenRouter (как в A2–A5, `litellm.completion(model="openrouter/...")`)
   или через прямой Anthropic-совместимый провайдер (Zhipu/GLM API напрямую).
   Это не мелочь: другой эндпоинт может иметь свои дефолты
   temperature/system-обёртки и незаметно изменить результат независимо от
   того, работает ли сам скилл. Если OpenHarness не даёт настроить именно
   OpenRouter как транспорт — зафиксировать это как отдельную переменную,
   которая мешает чистому сравнению «то же самое, только через скилл», а не
   молчать об этом.
3. **Батчевый режим.** README упоминает «structured JSON output for
   programmatic use» — это то, что нужно для прогона на 76 программах не
   руками; проверить его точный интерфейс в документации OpenHarness, а не
   предполагать по одной фразе.

Если после проверки окажется, что настоящий agent-driven вызов через
OpenHarness на 76 программах недостижим технически (несовместимый формат
skills, эндпоинт нельзя развязать от OpenRouter, батчевого режима нет) — это
фиксируется как честное ограничение эксперимента (аналогично тому, как A5
зафиксировал отступление от протокола по `rel-event` test timestamp), а не
тихо подменяется прямым вызовом модели с тем же текстом промпта.

**Что считать, тем же способом, что A2/A4:**
- CLEAN@k для k=1..5, по всем 76 программам;
- то же самое по механизму (`REVIEWS_NO_FILTER`, `SELF_AVAILABILITY_CANARY`,
  `PAYMENTS_NO_FILTER`, `VAR_MIXUP` — категории из `mechanism_labels.csv` и
  таблицы A2);
- cluster bootstrap 95% CI по `program_uid` (100000 выборок, тот же seed
  `20260915`, что в A4, для сравнимости методологии, не для буквального
  повторного использования тех же данных);
- стоимость и число вызовов (сравнить порядок величины с $0.1228 у A2).

## 4. Как сравнивать — правило решения, зафиксированное ДО прогона

Основной вопрос: **даёт ли починка через скилл тот же результат, что прямой
вызов из A2/A4, на тех же программах и той же модели?**

Критерий «полного мэтча» (все три обязательны):

1. **Парное сравнение, не только агрегат.** Точный тест Мак-Немара на 76
   парных исходах (skill-run CLEAN/не-CLEAN на программу против A2 CLEAN/не-CLEAN
   на ту же программу, по `program_uid`). `p > 0.05` — не найдено
   статистически значимого расхождения. Это тот же инструмент, что уже
   применялся как вторичная проверка в A4.
2. **Агрегат не хуже нижней границы A4.** CLEAN@5 (skill-run) ≥ 95.2%
   (нижняя граница 95% cluster bootstrap CI из A4) — не требуем точного
   совпадения процента, требуем «не хуже воспроизводимости, которая у нас уже
   есть между тремя повторами одного и того же прямого вызова».
3. **Нет нового класса отказа.** Любой провал скилла либо совпадает с уже
   известным (`deepseek-v4-flash-0731#79`, платёжный механизм — см. §1), либо
   получает отдельное объяснение в отчёте. Молча свалить новый механизм
   отказа в общий процент — нарушение конвенции `docs/experiments/README.md`.

Стоимость и число вызовов — не гейт, а диагностика: расхождение на порядок
(например, ×10 по стоимости или по числу вызовов на программу) фиксируется в
отчёте как практическое ограничение упаковки, даже если статистика по CLEAN@k
прошла.

## 5. Если не совпало — итерация

«Пока не будет полного мэтча» не означает бесконечный автономный цикл без
присмотра. Правило, симметричное дисциплине из `pilot_d_repair.py`/A2/A4
(там же капы на 3–5 итераций):

- Максимум **5 раундов переработки скилла** без обязательной остановки и
  проверки человеком (`docs/PLAN.md`-стиль: любой шаг, где агент не уверен,
  предлагается на подтверждение, а не проводится в обход).
- На каждом раунде: что изменено в `SKILL.md` и почему (гипотеза о причине
  расхождения — например, обёртка агента добавляет лишний текст, из-за
  которого модель теряет фокус на конкретной формулировке F1; или итерации
  обрываются раньше времени), затем повторный прогон **только по программам,
  где было расхождение с A2** (не по всем 76 — это дороже без дополнительной
  информации), затем повторная проверка критерия §4.
- Если после 5 раундов мэтча нет — это тоже результат: `negative` или
  `neutral` вердикт с честным описанием природы расхождения (например,
  «упаковка в скилл систематически ослабляет фокус модели на конкретной
  формулировке F1» — это самостоятельно интересное наблюдение о том, что
  «zero-configuration» не переносится на произвольный способ вызова
  бесплатно).

## 7. Что сделать с `docs/PLAN.md`

Этот план **не** редактирует `docs/PLAN.md` сам — по правилу из
`.claude/commands/continue.md` («изменения структуры плана... предложите это
текстом и подождите подтверждения»). Предлагаемый блок для вставки после
секции `C` (или в новую секцию `D`), на утверждение:

```
## D — Скилл-артефакт цикла починки

### D1 — Упаковка F1-цикла в скилл `pit-repair` + валидация паритета
- status: todo
- owner: —
- deps: H1 A2
- source: рабочие комментарии команды (переслано пользователем, см.
  docs/skill-artifact-plan.md), результаты A2/A4
- done-when: скилл `.claude/skills/pit-repair/SKILL.md` собран; прогон на
  тех же 76 программах и той же модели (`z-ai/glm-5.3-flash`), что A2/A4,
  даёт результат, проходящий критерий §4 плана (docs/skill-artifact-plan.md)
  ИЛИ задокументированное после ≤5 раундов переработки расхождение;
  отчёт docs/experiments/d1-skill-repair-parity.md закоммичен; указатель
  добавлен в pilot/REPORT.md; черновик формулировки для статьи предложен
  (не применён без утверждения).
```
